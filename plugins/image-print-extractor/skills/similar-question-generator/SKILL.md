# 同类题生成

本技能与 `image-print-extractor` 在同一插件内，共用其脚本目录 `<skill-dir>/../image-print-extractor/scripts/`（下文记为 `<scripts>`）、内容类型和 Word 导出能力。原题识别仍按提取技能执行；本技能只负责生成、验证和交付。

## 进入条件

- 来源一：提取技能完成后，用户在同类题邀请中回答要生成，或一开始就明确要求“提取后出同类题”。
- 来源二：用户直接给出清楚、完整的原题。先按提取技能把题目整理成带 `questions` 索引的 JSON，规则见 [题目结构](../image-print-extractor/references/questions.md)，再进入生成。
- 源题必须完整：全部小问、共享语篇或数据、关键条件和作答所需的图表都在，且题目已确认，没有未处理的 `〔〕`、`XXX` 或失败的插图。缺项时指出具体缺了什么，请用户补充或确认范围，不能凭猜测补题。`variants.py init` 会拒绝不满足条件的源题。
- 范围：涉及多道原题且用户没说清楚时，列出题号和题型，请用户选择。用户已指定的直接执行。

## 默认值与本次设置

| 项目 | 默认 | 可调整 |
|---|---|---|
| 数量 | 每道选中的完整原题 3 道 | 用户指定，1–10 |
| 难度 | 与原题相同（`same`） | 降低 `easier`、提高 `harder` |
| 教材范围 | 按模块默认教材，见 [学科规则](references/subjects.md) | 本次任务可临时放宽或修正 |
| 学生情况 | 无 | 年级、水平、薄弱点，只作用于本次任务（`--learner`） |
| 交付 | 可直接复制的聊天文本 | 用户要 Word 时另交 `.docx` |

识别不出模块，或原题与指定教材、年级冲突时，先说明冲突，等用户确认后再生成。不把本次的学生情况或范围保存成长期档案。

## 流程

1. 建立台账：

   ```text
   python -X utf8 <scripts>/variants.py init reviewed.json --run-id g1 --question q18 [--question q19] [--count 3] [--difficulty same|easier|harder] [--module M05] [--learner "初二，计算易错"] [--scope-override "只学到一次函数"]
   ```

   `reviewed.json` 是提取流水线的输出，在状态文件的 `files.export_source` 中可以找到。

2. 逐道写候选：每个变式位置（slot）单独写一个 JSON 文件，格式见 [候选格式](references/candidates.md)。每写完一道，运行：

   ```text
   python -X utf8 <scripts>/variants.py submit --ledger <ledger> --candidate <文件>
   ```

3. 看结果：`passed` 表示该位置完成；`failed` 时阅读 `failures`，只重写这一道，提交到同一 slot；`needs_review` 表示独立复核结论不确定，也要重写或复核。每个位置的尝试次数有上限（默认 3 次），用完即止，不能无限重试。
4. `status` 为 `ready_to_deliver` 后交付：

   ```text
   python -X utf8 <scripts>/variants.py deliver --ledger <ledger> --format chat|docx|both --output-dir <新目录> [--word-confirmed]
   ```

   只有用户确认要 Word 时才用 `docx` 或 `both`，并加 `--word-confirmed`。

## 写候选时的要求

- 以完整原题为单位：原题第 18 题有（1）（2）（3）问，每道新题也必须有（1）（2）（3）问，编号、顺序和前后依赖与原题一致。阅读题组保留“语篇＋对应问组”，重新核对每个设问和证据。
- 保持核心知识点、主要解法或任务能力、题型不变。通过改变情境、数据组合、条件呈现方式、干扰项或同等结构的材料，让三道题之间有说得清的训练差别。
  - 只改数字、近乎复刻原题，或三道题彼此雷同的，会被相似度检查拦下。
  - 也要防止改数据造成模型退化、条件冲突或无解。
- 难度：默认对齐原题的推理步数、知识综合程度、计算量、阅读篇幅、词汇句式和设问层级。降低难度可以简化数据、减少隐含条件；提高难度可以适量增加条件转换或推理环节。用 `design.difficulty_evidence` 写明依据。
- 原题有必要的图，新题也要配图，并且图要与新数据一致。技术图用提取技能的结构化绘图（`figure_drawing.py`、`figure_components.py`），白底黑线，渲染后逐张查看图片，确认与题面一致。
- 学生题面不得出现答案、解析、正确项标记或答案暗示。答案、解答过程和验证只写在 `internal` 中。

## 逐题验证（不能用自我声明代替）

- 写完题面后，换一个独立步骤重新求解：不看自己写下的答案，从题面出发逐问独立求解、代回验证，再把结果写入 `semantic` 检查的 `independent_answer`。脚本会比对它与 `internal.answers` 是否一致。
- 能计算的部分写确定性检查：数学用代入、求值、求根；物理用单位量纲和数值；化学用配平（元素和电荷守恒）和数值；英语用选项唯一性和证据句定位。各模块至少需要哪些检查，见学科规则。
- 开放写作、开放实验题不强求唯一答案：用 `rubric` 写出至少 3 条可核验标准，并确认任务、语言、条件和合理作答路径都可行。
- 再按模块清单逐项复核，写入 `review.checklist`，并在 `review.notes` 记录核对了什么。任一项不成立就写 `false`，该候选不通过。
- 修改题面、数据、选项、配图或依赖后，必须作为新候选重新提交、重新验证。旧的验证结论不能沿用。

## 交付

- 聊天：把 `student-chat.md` 的内容原样发给用户，不另加答案、解析或验证过程。
- Word：交付 `student.docx` 链接。该文件已自动检查：没有答案泄漏、与聊天文本一致，并且只由验证通过的题组成。
- 数量不足：用 `shortfalls` 中的原话逐题说明，例如“第18题目标 3 道，验证通过 2 道，缺 1 道”。部分交付和全部完成要分开说明。
- 答案与解析：只在 `internal/answer-key.md`，属于教师和内部材料，不放进学生文件夹。用户明确要答案时，可以单独提供，并说明它与学生版是两份材料。
- 不得把未提交、未通过或待复核的候选当作已验证题目交付，也不得编造文件或链接。
